Sécurité

Guide complet sur les mesures de sécurité et les bonnes pratiques pour utiliser l'API GestAgro de manière sécurisée.

HTTPS obligatoire

Toutes les communications avec l'API doivent utiliser HTTPS. Les requêtes HTTP non sécurisées sont automatiquement rejetées en production.

Ne jamais utiliser :

http://gestagro-api.onrender.com

Toujours utiliser :

https://gestagro-api.onrender.com

Protection des tokens

Stockage sécurisé

  • Ne jamais commiter les tokens dans votre code source ou Git
  • Utilisez des variables d'environnement ou un gestionnaire de secrets (AWS Secrets Manager, Azure Key Vault, etc.)
  • En applications web, utilisez des cookies httpOnly ou le sessionStorage (pas localStorage pour les tokens sensibles)
  • En applications mobiles, utilisez le Keychain (iOS) ou Keystore (Android)

Durée de vie des tokens

Access Token

Durée : 1 heure

Usage : Requêtes API authentifiées

Refresh Token

Durée : 7 jours

Usage : Obtenir un nouveau access token

Bonnes pratiques

  • Ne jamais exposer les tokens dans les URLs (query parameters)
  • Ne jamais logger les tokens complets (masquez les 4 derniers caractères)
  • Implémentez un mécanisme de refresh automatique avant expiration
  • Révoquez les tokens compromis immédiatement via POST /auth/logout/

Validation des données

Validez toujours les données côté client avant de les envoyer à l'API pour améliorer la sécurité et l'expérience utilisateur. 

// Validation avant envoi
function validateProduct(data) {
  const errors = [];
  
  if (!data.name || data.name.length < 3) {
    errors.push('Le nom doit contenir au moins 3 caractères');
  }
  
  if (!data.price || data.price <= 0) {
    errors.push('Le prix doit être supérieur à 0');
  }
  
  if (!data.currency || !['XAF', 'EUR', 'USD'].includes(data.currency)) {
    errors.push('Devise invalide');
  }
  
  return errors;
}

Prévention des attaques courantes

Injection SQL

L'API utilise des requêtes paramétrées et ORM Django pour prévenir les injections SQL. Vous n'avez pas besoin de prendre de mesures supplémentaires côté client.

XSS (Cross-Site Scripting)

Échappez toujours les données utilisateur avant de les afficher dans votre interface. Utilisez des bibliothèques appropriées selon votre framework.

CSRF (Cross-Site Request Forgery)

Les tokens JWT dans les headers Authorization protègent contre les attaques CSRF. L'API utilise également des tokens CSRF pour les requêtes de session.

Brute Force

L'API limite le nombre de tentatives de connexion par IP et par compte. Après plusieurs échecs, un délai d'attente est imposé.

Principe du moindre privilège

Utilisez des tokens avec les permissions minimales nécessaires pour votre cas d'usage.

  • Ne demandez pas d'accès administrateur si vous n'en avez pas besoin
  • Utilisez des comptes d'application dédiés plutôt que des comptes personnels
  • Révoquez les tokens inutilisés régulièrement
  • Auditez régulièrement les permissions accordées

Sécurité des webhooks

Vérification de signature

Vérifiez toujours la signature HMAC-SHA256 des webhooks pour vous assurer qu'ils proviennent bien de GestAgro. 

// Vérification de signature webhook
import hmac
import hashlib

def verify_webhook(payload, signature, secret):
    expected = hmac.new(
        secret.encode(),
        payload.encode(),
        hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(f"sha256={expected}", signature)

Checklist de sécurité

Communication

  • HTTPS utilisé en production
  • Certificats SSL valides
  • Pas de données sensibles dans les URLs

Authentification

  • Tokens stockés de manière sécurisée
  • Refresh automatique implémenté
  • Tokens révoqués lors de la déconnexion

Validation

  • Validation des données côté client
  • Échappement des données utilisateur
  • Validation des fichiers uploadés

Monitoring

  • Logs de sécurité activés
  • Alertes en cas d'activité suspecte
  • Audit régulier des accès

Signaler une vulnérabilité de sécurité

Si vous découvrez une vulnérabilité de sécurité, veuillez la signaler de manière responsable à security@gestagro.com.

Ne partagez pas publiquement les détails de la vulnérabilité avant qu'elle ne soit corrigée.
